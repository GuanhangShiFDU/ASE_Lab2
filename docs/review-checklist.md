本卡交付评审方法与记录位置；没有实现或启动微服务，也没有执行真实并发、鉴权、渠道或压力测试。下文“推演”指沿设计材料逐步追踪事实、消息和状态。静态校验只检查文档/契约的结构与部分一致性；历史卡片已记录的静态通过不自动变成本清单的人工通过。

## 使用方法与记录规则

1. 先固定实际被评审版本：在待审仓库执行 `git status --short` 和 `git rev-parse HEAD`。工作区干净后，记录完整 40 位 SHA、分支、材料来源、评审人和日期。不得仅填“最新 master”。若含未提交改动，先完成正常评审提交，或保留明确 diff 且不出具针对已提交版本的最终通过结论。
2. 按下方课程映射打开材料。每条检查的前提、步骤与预期在本文件，实际结果、证据、执行人/日期/SHA在 [逐项结果表](review-results.md) 的**同名 ID 行**，两者合起来是一条完整记录。一个检查含多子场景时，实际结果逐个记；有未检查或不通过子场景，整项不得记通过。
3. 依次核对总览和三条流程。评审人在指定版本内逐步追踪，不需要部署业务服务器。写清依据所在文件/章节/图节点/operationId，必要时保存图注或截图。只写“看过”“没问题”不足以重现结论。
4. 发现矛盾/遗漏，在 [问题记录](review-issues.md) 建立 DRI 编号，结果表引用它；附需求、原材料 SHA、影响、责任人、修复 PR/完整 SHA及复核结论。修复后只复查受影响项及其依赖，保留原失败记录，不覆盖历史。
5. 规则或流程有变更时，检查关联的模型、图源/导出图、HTTP/事件契约和恢复路径；更新这些项的被审 SHA。最终 #71200000 须明确各记录覆盖的版本，不能把多版本零散结论冒充一次完整最终验收。

结果状态另区分 **辅助核对符合预期**（已有 AI 阅读/推演证据，保留其身份和原版本，不算成员逐项复核）与 **进行中**（已完成部分实际步骤，明确剩余项）。**未执行**＝还未开展；**通过**＝该项所有子场景按材料核对且证据完整；**不通过**＝存在矛盾/遗漏；**阻塞**＝实际开始后因材料/依赖缺失无法继续，须写原因；**不适用**＝说明为何与当前方案无关，并由负责人实际确认。未执行不预填评审人、日期、结果 SHA或“通过”证据。

证据建议放 `docs/evidence/design-review/<完整被审SHA>/`，使用如 `DR-C04.md` 的文件名，记录双方提交顺序及引用。目录按真实发生创建，不放空图片或伪造日志。也可用可访问的 PR 评论/CodeArts 留言，包含完整链接及版本。截图需可读且不包含凭据。新一轮结果保存在该轮证据目录并从结果表引用，以便保留历史。

| DR-B05 | 超时/恢复 | 叫车或接单已提交但响应丢失 | 跟踪 getOperationResult 返回 NOT_OBSERVED/PENDING/已完成及权威读取；保持原意图重试 | 未知不新建相反操作；原键原内容恢复；成功记录可重放，不能把传输失败认定业务失败 |
| DR-B06 | 重复 | 相同调用者同一叫车/接单键，及同键改内容 | 对照幂等键范围分别推演；在原叫车成功后再过报价期限重放 | 同键同内容仅一个效果；异内容 IDEMPOTENCY_CONFLICT；已成功叫车不因报价后来过期变失败 |
| DR-B07 | 并发 | 一个乘客两个不同键叫车，或两订单抢同一司机 | 列出双方先提交的两种顺序并检查唯一约束和反馈 | 全局一个活动乘客单、司机一个活动分配；失败方收到冲突，派单建议不能越过 S-02 裁决 |
| DR-B08 | 并发 | 邀请仍有效，同版本接受与撤销/超时竞争 | 逐事务提交顺序检查邀请、订单、分配及事件生成 | 只提交一个合法结果；旧版本操作不能覆盖，失败方重读；不产生双司机或终态复活 |
| DR-B09 | 恢复 | S-02 已提交，MQ/派单工作进程中断 | 推演 Outbox 重投、消费任务恢复、重复事件及邀请重建依据 | 只恢复持久事实/任务并复核当前订单与期限，不重新创建同一意图订单或重复有效邀请 |
| DR-B10 | 恢复 | 客户端刷新/离线后重连，旧通知晚到 | 先读权威订单再处理通知，模拟通知失败/重放 | 显示当前状态和当前司机；旧通知不倒退状态；通知只是提示，失败不撤销接单 |

### 流程三：接驾、上车、行程与支付

[报告 4.3](design.md)、[行程支付契约](../contracts/http/trip-payment.md)、`pickup-trip-payment` / `trip-payment-recovery` 图；李全昊 #71199995。TP 编号来自[原场景记录](checks/trip-payment-71199995.md)，作为追溯，不继承通过结论。

| ID | 检查类别 | 前置条件 | 操作步骤 | 预期设计行为 / 判断标准 |
| --- | --- | --- | --- | --- |
| DR-T01 | 正常 | 已分配司机与合法订单，可靠计量（TP-01/05） | 逐步跟踪到达→确认上车并开始→结束→生成账单→核验收款 | 到达/开始/结束有服务端事实；上车和开始同事务；结束即释放履约占用，不等待计费/支付 |
| DR-T02 | 失败 | 他人、未分配司机、错误状态或客户端伪造金额（TP-02/11） | 分别推演操作权限、账单所属和可用支付方式校验 | 拒绝越权或非法推进；金额来自权威 Bill，客户端不能自行计价或代付他人账单 |
| DR-T03 | 并发/重复 | ARRIVED 取消与开始竞争，开始/结束原键重发或旧版本（TP-03/04） | 比较双方提交顺序、原键结果和新意图旧版本拒绝 | 一次合法转换；CANCELLED 不产生 Trip，IN_TRIP 不被普通取消；原成功可重放，重复结束不重计费 |
| DR-T04 | 失败/恢复 | 结束时无可信里程/时长；后续补计量或与结束竞争（TP-06/07/08） | 跟踪 measurement=null、补充第一份有效计量与原 BillingJob 恢复 | 完成不回滚；费用待生成不等于 0；第一份完整计量冻结，依据矛盾/旧规则缺失转复核，不静默覆盖改价 |
| DR-T05 | 正常/边界 | 最小费用、十进制费率、零费用单及取消费单（TP-09/10/26） | 核对精确计算、一次 HALF_UP 舍入及各账单收款入口 | 整数分、保留原规则/计量；Bill=0 无需付款且无虚构 Receipt；正额取消费沿用同一支付保护 |
| DR-T06 | 正常 | 本人正额 Bill 可付且无未决尝试（TP-12） | 跟踪尝试、稳定渠道请求号与发送任务先持久，再调用及核验结果 | 202/CREATED 只代表受理；经验证渠道事实唯一生成 Receipt 后才显示已付 |
| DR-T07 | 重复/并发 | 同键重发、同键异内容、异键同时支付同一 Bill（TP-13） | 检查幂等范围、未决槽位和返回 currentAttempt | 原键重放/异内容拒绝；仅一个未决尝试，其他意图不得额外扣款；客户端禁用按钮不替代后端原子约束 |
| DR-T08 | 恢复 | 发送工作进程在调用前/后崩溃（TP-14/15） | 从持久发送任务恢复并查询原 channelRequestId | 恢复稳定原请求号和原尝试；外部不支持幂等/查证时保留未知并人工处理，不承诺必然恰好一次扣款 |
| DR-T09 | 超时/恢复 | 渠道超时、查询 NOT_FOUND、自动重试预算耗尽（TP-16） | 追踪 UNKNOWN、未决槽位、持久对账/隔离路径和客户端提示 | 以上不是 FAILED_FINAL；保留未决锁，禁止新扣款；展示待确认/人工核查，不能诱导立刻再付 |

| DR-T13 | 超时/恢复 | 202 响应丢失、操作 SUCCEEDED、S-06 不可用及旧未付摘要（TP-21/22） | 分别查询操作结果、尝试与权威收款状态 | 操作成功不等于已收款；权威不可用为 UNKNOWN，不能以旧投影认定 UNPAID 并放开付款 |
| DR-T14 | 恢复/重复 | 账单工作进程崩溃、重复/缺失计量事件；通知失败/浏览器退出（TP-24/25） | 检查任务持久化、事实查询/稳定游标及重新进入费用页 | 计费和支付恢复不依赖客户端在线；唯一 Job/Bill，缺口可补；通知只提示，不回滚事实 |

## 可选的静态辅助检查

人工检查契约时可在独立 Python 虚拟环境安装既有检查器所需的 PyYAML、jsonschema、openapi-spec-validator，然后在仓库根目录运行：

```bash
python -X utf8 contracts/http/validate.py
python -X utf8 contracts/http/validate_cancellation.py
python -X utf8 contracts/http/validate_trip_payment.py
python -X utf8 contracts/events/validate.py
python -X utf8 contracts/http/validate_contracts.py
```

`-X utf8` 避免 Windows 默认编码读取中文材料失败。每条命令应分别检查退出码，失败时记录错误，不因后续命令成功覆盖前一次失败；保留实际 Python/依赖版本、命令及完整结果。依赖安装方法和已有 Windows 接收方实测见 [#71199996 检查记录](checks/core-api-71199996.md)。这些是文档/契约校验，不是业务单元测试、端到端或性能测试；人工核对业务语义仍须执行。
